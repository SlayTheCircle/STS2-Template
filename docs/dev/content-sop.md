# 内容开发 SOP（指导性质）

本页提供从设计稿到可玩 Mod 的推荐开发顺序。阶段可按设计依赖和项目进度调整、并行或跳过；内容与验证同步维护，具体硬约束单列在文末。

各阶段的具体写法、API 与坑位清单在对应模块手册里，本页只管「什么时候做、为什么这个顺序」。

## 推荐路径概览

```
设计稿归位 → 花名册先行 → 内容骨架 → 机制内核 → 美术映射
     →（可选模块：事件/世界线/对话）→ 数值迭代 → 验收发版
```

阶段之间不是瀑布：内容骨架和美术映射天然交替，「先让审计绿、再让画面美」是常见节奏。

## 阶段 0 · 设计稿归位

把设计者提供的原案放进 `local_dev/`（不入库），从中提取**公开摘要**到 `docs/history/design/`——原案对照、实现差异日志的格式见[设计输入说明](../history/design/README.md)。

为什么先做：后续每一步都要回查设计稿；「哪部分公开、哪部分私有」在动手前划清，比事后搬运便宜。设计稿没有版本纪律也不要紧——对照日志里注明「原案未标注日期」即可，不要替设计者静默改稿。

手工交付先做完整清点，再人工确认对应关系，不依赖固定 ZIP 目录：原案、升级表、机制说明、主卡、生成卡、遗物、药水、原版追加选项、新事件、章节、先古对话和美术槽各列一行范围与消费方。主卡表之外的生成牌同样计入设计范围；同名图、升级无变化和缺少作用域描述列为待裁定，不静默补写或只按文件总量判断齐全。

## 阶段 1 · 花名册先行

从设计稿整理 `docs/history/design/card-roster.txt`：每张卡一行（名＋类型），与后续本地化中文标题逐字一致。花名册是审计契约的锚点——[花名册审计](../../scripts/audit-roster.py)拿它核对「设计稿 ↔ 本地化 ↔ 实现类」三方一致。

为什么先做：这是「设计稿进代码」的第一道翻译，也是最容易出转录遗漏的地方：除卡牌外，先古对话、事件与剧情收尾同样需要逐项核对。**全族对照**——把设计稿从头到尾过一遍编号清单，比「想到哪张做哪张」可靠得多。后期发现遗漏就走同一流程补：对照 → 补条目 → 审计绿。

完整花名册先录，不为逐批变绿删减原案。同步填写 [roster-policy.json](../history/design/roster-policy.json)：`deferred` 是花名册中尚未实现的名称；`tokens` 和 `additions` 仅登记不在原案花名册中的已确认内容。原案生成牌优先直接列入花名册。配置为空代表没有这些例外。

## 阶段 2 · 内容骨架

先同步替换角色 StartingDeck／StartingRelics 和三池关联，再删掉示例类、双语键、花名册与美术映射；按目录约定（Attacks/Skills/Powers × 稀有度，Basic/Tokens 单独集中）铺内容类。每张卡三件套同步：**类文件 + 双语 loc + roster 一行**。每铺一小批跑一次 `./scripts/check.sh --source-only`。

为什么这个顺序：三件套不同步时，审计会立刻指出缺哪件——让机器当核对员。反过来说，如果你习惯先写完全部类再补 loc，也只是把核对推迟，不是不能做。写法照[卡牌手册](cards.md)（构造器四参、DynamicVar、升级、标签），踩坑清单在手册第 4 节，建议动手前通读一遍。

第一批可先让一张自家卡/遗物替换示例开局依赖，再删除全部不采用的示例类、键、花名册项和母版映射。其余计划卡保留在完整花名册并填 deferred；尚未采用的模板示例也不要冒充设计外新增。每批补类与双语文本后移除对应 deferred 名称、重导卡表，再运行源码检查。已实装项仍留在 deferred 会报错。

在自己的设计对照中维护轻量覆盖表：`设计项 | 消费方类/键/资源槽 | 已裁定规则 | 已实现 | 验收证据/未验证`。卡牌升级、三池、机制、遗物、药水、事件、章节与对话都列入；这张人工覆盖表补足花名册只验名称和数量的范围，不新增第二套自动身份配置。

## 阶段 3 · 机制内核

角色的核心机制（自定义 Power、关键词、token 卡）在这一步成形：机制 Power + `ModEntry` 关键词注册 + 词条悬停接线（卡牌走 `CanonicalKeywords`，遗物/能力/药水/附魔**没有该管线须显式挂**；具体写法见卡牌手册第 1 节）。

为什么在骨架之后：机制是内容的依赖项——卡面文本引用机制名词、数值挂机制变量。先把机制的地基打好，内容卡才有的接。也有项目反过来从机制原型起步（先做一张验证卡证明机制跑通，再铺量）——同样成立，验证卡别忘最后归位到花名册。

## 阶段 4 · 美术映射

`scripts/art/mappings.sh` 登记源文件完整相对路径→类名 → 配置母版目录 ART_SOURCE_DIR（组织内使用组织私有美术仓；外部维护者使用自己的输入）→ `scripts/prep-art.sh` 派生 → 缺件在写入前失败 → `check.sh --full` 让 audit-assets 全模式转绿。资源槽规格见[素材规范](assets.md)与[美术需求](../design/artwork.md)。

思路：映射表是「美术仓文件名 ↔ 代码类名」的唯一翻译层，登记完整比派生脚本写得多重要。Base 家族缺图自动回退占位，所以这一步可以晚于内容存在——但**上线前必须归零占位**，否则图鉴/卡面全是占位图。派生脚本的确定性约定（字节比对、不按 mtime 判断）直接沿用 `art/common.sh` 的 convert 包装，别绕开它。

## 阶段 5 · 可选模块

事件、世界线、先古对话按需接线——手册是[事件](events.md)与[世界线](worldline.md)。这批模块的共性：**接线契约在公开文档，代码按同版本原版先例与 RitsuLib API 实现**（模板骨架不含，理由见 worldline 开头）。建议等内容主体稳定后再做——它们多为战斗外围体验，返工成本低于核心卡组。

## 阶段 6 · 数值迭代

设计者平衡批次（V1/V2/V3…）：每次批次 = 设计稿对照改动 + 双语文本同步 + `export-card-table.py` 重新生成卡表 + CHANGELOG 记账。数值改动几乎都走 DynamicVar，卡面自动跟随——这正是阶段 2 把数值全部变量化的回报。设计者的裁定口径（废案保留资产、机制语义定案）记录进对照日志，不散落在提交信息里。

## 阶段 7 · 验收与发版

`check.sh --full` → `build.sh` 完整构建 → 部署到游戏试玩（**游戏递归扫描 `mods/`：先关游戏、备份移出 `mods/`**）→ 设计者/维护者验收 → 按[新仓上手](onboarding.md)第 5 节发版（CHANGELOG 段落 → tag → 草稿 → 验收 → 双端发布）。

源码与完整本机检查允许显式声明的开发批次，供逐批构建/试玩；package.sh 在生成发行候选包前执行 `audit-roster.py --release`，要求 deferred 清零。非卡内容按覆盖表逐项验收，明确此次发行的设计范围和未验证场景；不能把 tokens/additions 当成允许原案缺项的通用白名单。

验收记录进 STATUS（证据边界：哪些游戏内验过、哪些只过了 CI）。CI 绿不等于游戏内验收——这是[验证纪律](testing.md)的核心。

## 硬约束与软建议

**真正的硬约束**（违反会炸构建或审计）：

- 清单是身份唯一来源：mod id 恰为 `STS2-<PascalName>`，文件名与 id 一致；
- 三方一致：roster ↔ 本地化标题 ↔ 实现类计数；
- 双语键集一致；loc 占位符必须对应真实变量；
- 多媒体不入公开仓；`local_dev/` 整体不入库；
- CHANGELOG 缺版本段会让 Release 构建中止。

**其余都是软建议**：阶段顺序、批次大小、先机制还是先内容、美术何时进场——按项目节奏来。判断标准只有一条：**每一步之后对应风险是否有正确证据**。源码审计不覆盖全部运行行为；机制、界面与存档变更仍需实际游戏验收，顺序按项目安排。

## 常见返工模式（前车之鉴）

- **转录遗漏**：设计稿有、代码没有（整段对话/收尾句漏转）。对策 = 阶段 1 的全族对照习惯。
- **声明滞后**：文本写了机制名词、类上没挂声明 → 悬停无注释。对策 = 内容与词条声明同批提交。
- **卡表手改**：`docs/design/cards.md` 归生成器所有，手改必被审计打回。永远跑 `export-card-table.py`。
- **数值硬编码**：卡面文本写死数字，平衡批次一到每处都要手改。对策 = 阶段 2 一律 DynamicVar。
- **部署抢跑**：游戏开着就覆盖安装。对策 = 部署脚本已内置进程守卫，别绕过它。

## 与模板骨架的关系

模板自带的示例件（示例打击/防御/昂扬、坠饰、药剂、特训）就是阶段 2-3 的最小示范：删掉它们、照着同样的三件套节奏铺你的内容即可。示例件同时是「审计在空仓库上怎么叫」的参照——铺内容前先跑一次 `check.sh --source-only` 看绿的样子，之后每次变红就知道是新引入的。

## 制作自定义角色动画

首次制作先完成[动画入门](animation/README.md)的几何示例，再做母图、部件、短动作与游戏接入。每阶段提供明确版本的预览，后续动作在接线与显示尺寸确认后展开。
