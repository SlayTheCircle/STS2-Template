# 开发与发布工作流

## 当前阶段

仓库已公开，主线开发在 main 上进行。用户明确要求后才提交、推送、创建 PR、合并、打 tag、部署或重写历史。日常实施先形成可审查的 diff 与验证结果。

分支模型保持轻量：是否开短分支由维护者逐案决定，分支只承载单一意图，完成后删除，不设 develop／release／hotfix 常设分支。模板仓的贡献分支与 PR 用于审阅，接受的改动按下述单快照策略写入 main；派生 Mod 仓可通过 PR 合回 main 并保留正常开发历史。远程分支保护规则按维护者决定配置。

## 模板仓历史策略

本节仅适用于上游模板仓 `SlayTheCircle/STS2-Template`。其 main 始终只保留一个无父提交的根提交，提交主题采用英文 `chore(init): <summary>`，内容代表当前完整模板快照，以保持模板主线的纯净性。每次更新在完成审阅与相应验证后，重新生成单提交快照，并通过 `force-with-lease` 覆盖远程 main，不累积增量提交或合并提交。

推送前须读取并核对远程 main 的预期提交，使用绑定该提交的显式租约 `--force-with-lease=refs/heads/main:<expected-commit>`。租约检查失败时停止，重新检查远程变化，不改用无条件 `--force`。变更说明、审阅结论与验证证据由 CHANGELOG、STATUS 和相应文档维护。

派生 Mod 仓（`.template-origin` 的 `derived` 非 null）保留正常开发历史，使用 Conventional Commits。模板单快照策略规定更新方式；会产生外在影响的操作仍需维护者授权。

## 按风险交付

| 变更 | 最小检查 | 评审 |
|---|---|---|
| 文档与小型维护 | 源码检查、链接与过时术语 | 本地可审查结果；公开 PR 按范围审查 |
| 普通内容修复 | 源码检查、DLL 编译、相关游戏行为 | 小范围 PR 审查 |
| 核心机制、钩子、持久化、跨模块重构 | 完整构建、对应边界与负向场景、真实试玩 | 未参与实现的独立 CR |
| 发布候选 | 完整环境与发行物验收、兼容矩阵、回退材料 | 独立 CR 与维护者接受 |

大型跨领域工作先在私有工作区写目标、边界、失败模式和拆分方案。评审结论采用 Blocking、Should-fix、Nits、Verified claims；Blocking 合入前修复，Should-fix 修复或记录延后理由。尚未部署 Bot Review，不把其他仓库的机器人机制列为当前门禁。

## 提交与文档

提交信息一律使用英文，主题与正文分别经 `-m` 提交。模板 main 使用上述 `chore(init)` 快照主题；贡献分支及派生 Mod 仓遵循 Conventional Commits。修改拥有该事实的文档，交付前搜索旧版本、命令、路径和机制术语。日常 CHANGELOG 草稿可存于私有目录并附在 PR 描述，发布前按新增／变更／移除／修复等类别汇总；不记录提交哈希流水账。

## 发布流程

本节适用于派生 Mod 仓。模板仓自身维护源码快照，不发行或打 tag；更新 main 遵循模板仓历史策略。

1. 冻结清单版本、候选提交、游戏和 RitsuLib 对应关系、CHANGELOG 段落及发行范围。
2. 完成源码检查、编译、完整素材和 PCK 验证；在真实游戏验证安装、角色、核心机制、事件、世界线与必要读档／原版联动。记录未完成项，不能用 CI 替代试玩。
3. 在已接受的 main 上打 `v*` tag 并推送：已配置的 Release 工作流在托管 runner 检出自己的私有构建输入与美术母版仓，完成完整构建，校验 tag 与清单版本一致，从 [CHANGELOG](../../CHANGELOG.md) 提取发行说明，创建草稿 Release。配置见[新仓上手](onboarding.md)；未启用私有输入 CI 的维护者可在本机 package.sh 生成候选包。fork PR 拿不到 secret，不会触发私有输入构建。
4. 维护者下载草稿 Release 的发行物试玩验收，保留上一验收包与存档备份说明；通过后手动发布。tag、Release 和发行包版本一致。
5. 发布后在 main 上更新当前状态、下一开发目标与 CHANGELOG。

公开仓不收纳美术母版与游戏引用；正式版宣告由维护者验收草稿后手动完成。
